# 詳細設計 初稿 v0.1

作成: 2026-09-06。技術検証前の設計を固定した記録。承認済み requirements.md を変更しない。検証後の現行設計は detailed-design.md とする。

## 構成と責務

Godot 4系＋GDScriptをエンジン候補とし、正確な版とWindows出力は別の採用ゲートとする。ゲームを MatchRules（純粋な状態遷移）、HostSimulation（60 Hz）、ClientPrediction、Presentation、Transport、RecoveryStore、Settings に分ける。練習は同じシミュレーションをローカルで駆動する。

ホストが移動の最終位置、命中、アイテム、乱数、得点を決定。クライアントは入力を送信し、自分の移動を先行表示する。描画フレームと物理tickを分離する。通信方式変更でルールを変更しない。

## 試合状態機械

Connection → SelectingFirst → SelectingSecond → Countdown → Fighting → Resolving → 次のSelectingFirst / MatchResult。接続断ではSuspendedへ入り、確定記録照合後に切断敗北を一度だけ適用する。最大60秒で復帰を打ち切る。

選択10秒ずつ、カウントダウン3秒、戦闘90秒。ホストtick基準の期限を配信する。10勝先取。引き分けもラウンド番号を進める。アーマーはラウンド1–3=50、4–7=75、8–11=100、12以降125。

## 通信契約案

- 入力: tick、sequence、移動軸、視点、押下/解放、action ID。古い入力・未来入力・範囲外値を拒否する。
- 状態差分: server tick、acknowledged input、位置速度、行動、体力、弾、投擲物。20 Hzを初期案とする。
- 確実配送: 参加認証、地点確定、所持品変更、決着、復帰。イベントIDで重複排除。
- 接続はゲーム内EOSが第一候補、ENet直接接続で開発、必要なら許容済み補助ソフト。実際の経路は未採用。

## 戦闘と装備

同じtickの全ダメージを集計してから死亡を判定。実体弾は前位置から次位置までsweepし、命中した最前面の面で消滅する。初期案では過去位置への巻き戻しを行わない。回復は開始・中断・完了をホスト管理し、完了時だけ在庫消費。交換長押しは対象と開始tickを固定し、範囲外・視線逸脱で取り消す。投擲は構え・照準・放出を区別し、放出時だけ消費する。

## 復元案と検証仮説

試合ID、両プレイヤーID、ルール版、ラウンド番号、確定スコア、決着ID、ペナルティIDを両者が保存。一時ファイルを書いてから本体へ置換する。戦闘位置・飛翔弾は復元せず、切断したラウンドを決着させて次へ進む。

初稿の仮説:

1. ホスト確定→ローカル保存→ゲスト送信→保存ACKで、終了タイミングによらず両者が一致できる。
2. 記録のハッシュと世代番号で新しい記録を選べる。
3. ラウンド番号をペナルティIDに含めれば、決着直後の切断でも二重敗北を避けられる。
4. 一時ファイル置換で保存中の強制終了に耐えられる。
5. 切断時刻＋60秒を保存すればホスト再起動にも対応できる。

これらは未検証であり、特に分岐記録、同時切断、時計変更、双方のACKが届いたことの合意は未解決。

## 試作計画

エンジンに依存しないNode.js標準ライブラリだけのUDP試作を作る。2つのOSプロセス、実ファイル、強制終了、再起動を用い、損失・重複・並べ替え、片側だけ最新、同世代分岐、保存途中終了、得点重複、期限超過、10勝終了を試験する。設計の論理検証とGodot/ENet/EOSの実証を区別する。

合格条件: 合法な履歴だけを採用し、復帰を繰り返しても同じラウンドで得点が増えず、同一系統の新しい記録へ収束する。分岐・破損・責任不明時は推測で得点を変更しない。
