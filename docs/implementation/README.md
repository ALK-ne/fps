## 「ワンショット」の契約

実装担当は上から読んだ後、06のW01からW12を順に進める。途中で数値・ファイル構成・画面の細部をユーザーへ聞き直さない。失敗した試験を修正して再実行し、ゲームを一部だけ作って完了報告しない。明示した外部依存に達しても、それに依存しない作業は最後まで進める。

成果は3段階で表示する: `implementation_complete`（全コード・配布物・ローカル受入成功）、`two_home_verified`（実2家庭で接続/復帰成功）、`player_accepted`（ユーザーが操作感を合格）。承認済み要件上の完成は3つすべて。後ろ2つを前者から推測しない。

PC2台、相手側の補助ソフト認証、ユーザーのプレイ評価は実装エージェントだけでは代行完了できない。設計の曖昧さとは別の外部条件として扱い、用意されたチェックリストと実行物を渡す。

責任不明の切断については08のD08に例外案を1つ定義している。ユーザーの回答が来るまでは「承認済み」と記録しない。実装は例外ハンドラーと試験まで作れるが、このルール変更の承認なしに正式な受入完了とは扱わない。

## 固定する範囲

Godot 4.7.2 Standard（非.NET）、GDScript、Compatibility renderer、Godot Physics、Windows x86_64。通信はENetConnectionを直接包み、RPC/MultiplayerSpawnerと混在させない。外部Godotアドオン、EOS、専用サーバー、対戦ボット、アカウント機構は初版に導入しない。

内部名は`ArenaDuel`、表示名は`Arena Duel Prototype`。正式名称が後から決まってもセーブパスとプロトコルIDは変えない。値はspec.jsonから製品Resourceを生成する。将来チューニングするときはspecと対応する期待値を同時更新する。

## 今回の設計チェック

`node tools/validate-design.mjs` で設定、作業依存、受入対応、配置の左右対称性、スポーン間の経路/射線を確認する。これはGodot上の物理試験を置き換えない。実装仕様が機械的に矛盾していないかを確認する補助である。

最終結果は[design-validation.json](design-validation.json)。6分類の静的検査を通過し、6spawnすべてに有効な後手が3–4か所ある。既存Node試作の17試験と、未実施の製品用38受入定義を区別する。
