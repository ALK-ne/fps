## 2. エンジン案

第一候補: **Godot 4系の安定版＋GDScript、Windows x86_64出力**。

- 無償のMITライセンスで、Windowsへの実行ファイル出力を備える。[Godotライセンス](https://godotengine.org/license/)、[Windows出力](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)
- 標準でENetによる通信とホスト・クライアント初期化が使える。[マルチプレイヤー公式資料](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- この規模の幾何学的なアリーナ、トゥーン表現、2人対戦には検証候補として妥当と判断。これは設計上の推奨であり、性能保証ではない。
- GDScriptにより現状の古い.NET SDKへの依存を避ける。EOS等のネイティブSDK統合には別途拡張またはバインディングが必要になりうる。
- 開始時に安定版の正確なバージョンと対応するexport templateを固定する。まだインストールも採用確定もしていない。

## 3. 外部接続の候補

ゲーム単体接続を優先する要件を維持する。LANで接続できても、この要件を達成したとは判定しない。

| 方式 | 状況 | 採用前に確認すること |
| --- | --- | --- |
| Godot＋ゲーム内に組み込むEOS | 単体接続の調査第一候補。EOSは無料サービスとP2Pを公開している | Godot用統合手段の保守状況・SDK対応・登録設定・認証・実際のNAT越え・中継・配布条件 |
| Godot標準ENetの直接接続 | ローカル試験に向く。インターネットでは家庭のルーター設定等が必要になりうる | UDPの到達性、ルーター設定を不要にできるか、2回線での確認 |
| ENet＋Tailscale | ユーザー許容済みの補助ソフト経路候補 | 双方の導入・認証・ネットワーク共有、実測遅延。ゲーム単体接続ではない |

根拠:

- Godot公式は家庭からのインターネットホストにUDPポート転送が必要になりうることを説明している。[Godot Hosting considerations](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html#hosting-considerations)
- EOS公式は無料のサービス群にPeer-to-Peerを含めている。[EOS公式](https://onlineservices.epicgames.com/?lang=en-US)
- Epicの公式サンプル資料はプレイヤーホストとEOS等によるP2P NAT越えの関係を説明している。ただしUnreal向け資料でありGodot統合の証明には使わない。[Common User Plugin](https://dev.epicgames.com/documentation/en-us/unreal-engine/common-user-plugin-in-unreal-engine-for-lyra-sample-game)
- Tailscale Personalは確認時点で個人向け無料・最大6ユーザー。1対1用途の補助経路候補になる。[Tailscale料金](https://tailscale.com/pricing)

EOSの詳細NAT P2P資料は取得時に本文が読めなかった。したがって特定の認証方式やGodot拡張の互換性、全環境での接続成功は確認済みとしない。
agent-reachのJina Readerはネットワーク接続に失敗したため、Webブラウズで公式情報を確認した。

## 4. ゲーム内設計案

- ホストが得点・ラウンド進行・ダメージ・アイテム取得・乱数結果を管理。
- 自分の移動は即座に表示し、ホストの判定と補正。他プレイヤーは補間表示。
- 弾は移動経路に沿って衝突を検査し、高速な弾が壁やプレイヤーを通り抜けない設計にする。
- ラウンド決着前に同じシミュレーション時刻のダメージをまとめて処理し、同時死亡を判定する案。
- 通信層を分離し、LAN試験から外部接続サービスへ置き換えてもゲームルールを変えない。
- 地点候補は全候補について後手に有効な候補が残るよう検査。ランダム選択にも同じ制約を適用。
- 回復・拾得・交換・投擲を明示的な状態として管理し、中断時の二重消費を防ぐ。

これらは実装設計案。命中補償、重力による弾道変化、攻撃間隔などの詳細は評価可能な初期値として明文化する。

## 5. ホスト再起動からの復元

最も早く検証する項目の一つ。単なる再接続APIでは完了しない。

両者に保存する案:

- 試合ID、ルール版、プレイヤー識別、ホスト識別。
- 確定した両者の得点、ラウンド番号、最後の決着ID、直前の選択順。
- 進行フェーズ、再接続期限、切断ペナルティの処理ID。

保存は一時ファイルから置換し、終了直前の書き込み中断も検証する。
復帰時は同じ試合・同じ参加者であることと保存状態を照合し、切断による敗北は一度だけ適用する。
死亡確定直後の切断で既存の敗北へさらに得点を加算しない。

**限界:** 2台だけでは通信断がどちらの責任かを常に客観的に特定できない。両者同時切断や保存状態不一致の扱いは未確定で、追加の設計判断が必要。通常の片側切断とホスト再起動の要件は維持する。

## 6. 実装・検証の順序案

1. エンジン固定、Windows出力、2プロセス接続、保存と再起動復帰の小規模検証。
2. 外部接続方式の検証。異なる家庭回線の2台で、初回接続・再接続を確認する。
3. アリーナ移動、ライフル、固定・移動標的で操作感を評価。
4. 全3武器、弾薬、拾得、4回復、2投擲を統合。
5. 地点選択、10勝制、アーマー進行、引き分け、再戦を統合。
6. トゥーン表現、音・ヒット演出、設定保存、配布物と最終2台試験。

順序は調整可能だが、単体の射撃デモだけを完成扱いにしない。

## 7. 受け入れ検証リスト

- 第4/8/12ラウンド境界と、引き分けを挟んだ強化。
- 時間切れの体力＋アーマー比較、同値、同時死亡。
- 選択タイムアウト、先手後手の抽選、距離制約、最大23秒、アイテム非表示。
- 交換長押し・回復中断・弾切れ・投擲で所持品が二重消費されない。
- 弾の飛翔、遮蔽物、自傷半減、焼夷の着火位置。
- 遅延・パケット損失時の移動、命中、アイテム競合、ラウンド終了。
- 戦闘中・選択中・決着直後の切断、60秒以内復帰、期限超過、10勝到達。
- ホスト強制終了→再起動、保存途中終了、復帰ペナルティの二重適用防止。
- 設定の再起動後保持、練習モード、10勝後再戦。
- 実機解像度、FPS、フレーム時間、ネットワーク遅延を記録。性能合格値は友人PCと試作の計測後に決定。
